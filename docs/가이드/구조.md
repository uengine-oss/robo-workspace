# 1. 돌아가는 모양

## 1-1. 프로세스 둘 + 컨테이너 일곱 (또는 아홉)

```text
Windows 프로세스 (Docker 밖)
  Robo-Architect.exe      화면(Electron)
  python.exe              Architect 백엔드 — 설치 폴더 안의 **번들 파이썬**
                          resources\runtime\architect\python\python.exe
                          127.0.0.1 의 **동적 포트**에 붙는다 (실측: 64322)
                          └ 고정 포트가 아니다. 옛 문서의 "59010" 은 지난 값이다

Docker 컨테이너
  analyzer · catalog · fabric · gateway        ← PC 가 띄운다 (일곱)
  parser · pdf2bpmn · wireframe
  graph-db · graph-bolt                        ← **어디에 두느냐가 갈린다**
```

백엔드만 Docker 밖에 있는 이유: **Windows 파일 경로와 Claude PTY 를 직접 써야** 해서다.
컨테이너 안에서는 사용자의 프로젝트 폴더에 닿지 못한다.

## 1-2. 구성이 둘 — **저장소를 어디에 두느냐**

```text
bundled   compose.yml 만                     PC 안에 DB 까지. 컨테이너 **아홉**.
                                             1인 도구다. 공유·초대가 성립하지 않는다
central   compose.yml + compose.remote-graph  DB 는 한 곳에 하나(compose.central-db),
                                             PC 는 나머지 **일곱**만 띄운다
```

프로젝트·권한·공유는 모두 그 저장소에 있다. **팀이 같은 설계를 보려면 저장소가
하나여야 한다** — 그래서 central 이 납품 구성이다.

> msa-ez 의 `docker-compose.split.db.yml` / `.ap.yml` 과 같은 이유의 분할이다.
> 다만 그쪽은 *서버 내부* 분할이고, 여기서는 **서버와 PC** 를 가른다.

## 1-3. 주소 — `localhost` 가 안 되는 이유

`ROBO_GRAPH_HOST` 에 넣은 값은 **PC 의 컨테이너 일곱에도 그대로 들어간다.**
컨테이너 안의 `localhost` 는 자기 자신이므로 앱이 아예 거절한다.

```text
거절한다   localhost · 127.* · ::1 · 0.0.0.0 · host.docker.internal
쓴다      그 기계의 **사내망/LAN 주소** (실측 예: 192.168.219.185)
쓰지 않는다 vEthernet (WSL) 주소 (172.27.*) — 다른 PC 가 못 닿는다
```

> 실측(2026-10-14): DB 를 `192.168.219.185:5432·7687` 로 열었을 때
> **컨테이너 안에서 닿는다**. 같은 포트를 WSL 주소나 `host.docker.internal` 로
> 부르면 닿지 않는다 — 공개 주소를 그 IP 에만 묶었기 때문이다.

## 1-4. 기동 전에 차 있어야 하는 것 — **두 부류를 가른다**

⚠ **"기동을 막는 것" 과 "없으면 기능이 실패하는 것" 은 다르다.** 한 덩어리로
보면 **앱은 떴는데 분석이 조용히 실패하는** 상태에 빠진다.

```text
① 기동을 막는다   `runtime-manifest.json` 의 `credentialNames` 에 적힌 이름
                 하나라도 비면 창이 안 뜨고 `runtime.credentials_missing` 으로
                 멈춘다. 앱이 보는 것은 **그 목록뿐**이다(docker-stack.ts)
                 ⚠ **개수가 릴리스마다 다르다** — 계약서
                   (`release-environment.json`)에는 **열여섯**이 적혀 있지만,
                   매니페스트에는 **굽는 기계에 값이 들어 있던 이름만** 실린다.
                   2026-10-22 판은 **셋**이다
                   (AUTH_JWT_SECRET · OPENAI_API_KEY · ROBO_LLM_API_KEY)
② 없으면 기능이 실패한다   앱은 멀쩡히 뜬다. 그래서 더 늦게 드러난다
                 AUTH_ROLE_SECRET      → 프로젝트를 **열 수 없다**
                 AI 키 별칭 넷          → 분석·탐색이 **그때** 실패한다
                 PDF2BPMN_FACADE_KEY   → 문서 변환이 실패한다
                 AUTH_DEV_LOGIN_ACCOUNTS → 시험 로그인이 안 된다
```

> **숫자를 외우지 않는다.** 그 릴리스의 매니페스트가 말하는 대로 본다 —
> 문서에 적힌 개수는 **그날의 사진**이다.

`AUTH_ROLE_SECRET` 이 공용이어야 하는 이유: 사용자 한 명 = DB 계정 하나이고,
그 계정의 비밀번호를 **HMAC-SHA256(이 값, 사번)으로 계산해 낸다**(저장하지 않는다).
**한 번 정하면 못 바꾼다** — 바꾸면 그 PC 가 자기 프로젝트를 못 연다.

## 1-5. 로그인 전에 DB 가 한 번 초기화돼야 한다

```text
안 하면   로그인이 **503 AUTH_NOT_INITIALIZED**. 개발용 로그인도 같이 막힌다
왜        app_auth_policy 의 initialized 가 false 이거나 표가 아예 없다
앱이 안 함 store.py 의 ensure_schema() 는 "서버 운영 명령 전용"이고
          앱 안에 **호출하는 곳이 없다**
누가 함    robo-authority 이미지 안의 `scripts.accounts_admin`
          (설치 EXE 에는 들어 있지 않다)
순서      migrate → grant(최초 관리자) → policy
          **grant 가 initialized 를 켠다.** policy 를 먼저 부르면 거절된다
```

## 1-6. 식별자가 둘 — **우리 것과 기업 것**

```text
우리 것      프로젝트 `prj_` + 난수 10자리 · 적재 세션 uuid 앞 8자
             ⚠ 프로젝트 id 는 **그대로 Postgres/AGE 의 graph 이름**이다
             규칙 `^[a-z][a-z0-9_]{0,62}$` — 하이픈도 대문자도 못 쓴다
기업 것      **서비스 ID**. 사람이 적는다 (2026-10-22 추가)
             프로젝트: 만들 때 한 번 · 적재: 돌릴 때마다
             모양 `ROBO-2026-001` · `HR_LEAVE_01` · `erp.billing.v2`
```

> **왜 가르나.** 기업 체계의 값을 graph 이름에 넣으려면 변형해야 하고, 그러면
> 두 값이 어긋난다. 가르면 나중에 "바꿀 수 있게" 바꾸는 날도 **그래프를 다시
> 쓰지 않고** 한 줄 UPDATE 로 끝난다.

```text
누가 정하나   **프로젝트 소유자만**. 편집자는 적재는 하지만 ID 는 못 붙인다
바꿀 수 있나  **없다.** 고치는 화면도 API 도 두지 않았다 — 그게 강제다
유일한가      프로젝트는 **DB 유일 인덱스**가 지킨다(대소문자 무시)
              적재는 지난 run 기록을 조회해 막는다(인덱스를 못 거는 이유는
              하이브리드→ES 승격이 같은 세션 id 로 두 번째 행을 쓰기 때문)
비워도 되나    된다. 비우면 지금처럼 난수 id 를 쓴다
기존 프로젝트  값이 없다. 부분 인덱스라 서로 부딪치지 않는다
사는 곳       `app_projects.value->>'serviceId'` (+ 생성열 `service_id`)
              `app_ingestion_runs.session_id`
```

> ⚠ **스키마 추가를 올리는 것은 운영 명령뿐이다.** 열 하나 + 부분 유일 인덱스가
> 새로 생겼는데, 중앙 구성에서 `/api/projects` 를 서비스하는 것은 **authority
> 서버**이고(`api/authority.py` 가 projects_router 를 싣는다) 거기서는
> `ensure_schema()` 가 표가 있는지만 보고 **DDL 을 돌리지 않는다** — §1-5 와
> 같은 자리다. 올리는 것은 `scripts.accounts_admin migrate` 이고, 그 절차는
> `관리자-DB올리기.md` 의 **"새 릴리스로 올릴 때"** 에 있다.
>
> 안 올린 DB 에서는 `serviceId` 가 **그냥 들어가고 겹쳐도 아무 일이 없다.**
> 그래서 앱이 `pg_class` 에서 인덱스를 먼저 찾아보고, 없으면 **서비스 ID 를
> 거절한다**(`store.service_id_guard_ready()`). 조용히 틀린 데이터보다 거절이
> 싸다. ID 를 비우면 그 DB 에서도 프로젝트는 만들 수 있다.

# 2. 받는 것 — 릴리스 폴더

```text
Robo-Architect-Setup-<releaseId>.exe   106MB   앱 껍데기 + 번들 Python + compose 셋
robo-images.tar                        1.95GB  이미지 **열** (1.82 GiB)
SHA256SUMS                                     위 둘 + 아래 것들의 체크섬
runtime-manifest.json                          이미지 이름·image id·source pin·비밀 이름
central-server/                                DB 를 세우는 쪽 (compose · env 예시 · README)
sbom/                                          **CycloneDX 11 + SPDX 11** · INDEX.md · 체크섬
```

> **`sbom/` 은 굽기가 만든다** (2026-10-22 부터). `robo.ps1` 의 release 가
> `scripts/sbom-release.py` 를 릴리스 폴더에 대고 돌린다(`docker scout sbom`).
> 그 전에는 손으로 돌리는 단계였고, 그래서 한 판은 굽기가 끝난 한참 뒤에야
> 생겼다.
>
> ⚠ **실패해도 릴리스를 깨지 않는다** — scout 는 취약점 DB 를 물어보므로 망이
> 없으면 못 뽑는다. 그때는 경고와 함께 손으로 돌릴 명령이 찍힌다. 건너뛰려면
> `-SkipSbom`. **납품 전에 `sbom/` 이 있는지 눈으로 본다.**
>
> 두 형식을 같이 내는 이유는 받는 조직이 쓰는 도구가 갈려서다 — 같은 날 같은
> 이미지에서 뽑았으므로 내용은 같다(SPDX 쪽이 이미지 자신을 한 항목 더 센다).

`releaseId` 는 폴더 이름이자 **이미지 태그**다 — 예:
`0.1.0-w1a0b7933-af428665f-s1a7f6d-rint-none`
(`w`=workspace 커밋 · `a`=architect 커밋 · `s`=소스 다이제스트 · `rint`=internal-test 채널).

## 이미지 신원을 세 번 확인한다

```text
굽을 때    매니페스트에 이름과 **sha256 image id** 를 같이 적는다
로드 전    tar 의 SHA256 을 검사한다
로드 후    id 를 **다시** 대조하고, 안 맞으면 기동을 멈춘다 (docker-stack.ts ensureImages)
```

**태그만 같고 내용이 다른 이미지로는 못 돌아간다.** 그래서 서버에도 PC 와 **같은 tar**
를 올려야 한다 — 태그에 릴리스 id 가 박혀 있다.

# 3. 만드는 것 — 빌더만 본다

> **아래 경로는 굽는 기계에만 있다.** 쓰는 PC·DB 서버에는 없고, 없어야 맞다
> (§0 의 "소스 저장소는 쓰는 PC 에 존재하지 않는다"). 다만 `robo-workspace`
> **저장소 자체는 살아 있다** — 커밋 앞 8자리가 releaseId 의 `w` 자리이고
> 이미지 태그 10개에 전부 박힌다. 다음 릴리스를 구울 때 다시 받는다.

## 3-1. 한 장 요약

```text
robo-workspace                 오케스트레이터. 코드가 없다
  workspace.json               무엇을 어디서 어느 브랜치로 받을지, 어떤 포트로 띄울지
  scripts/robo.ps1             setup · up · release 가 전부 여기
  .env                         **모든 서비스의 비밀과 설정이 여기 한 곳**
  release-environment.json     그 .env 를 서비스별 파일로 쪼개는 규칙

        ↓ setup 이 클론

<workspace 부모>/project/      ← workspace 옆이 아니라 **부모 밑의 project**
  robo-architect               앱 본체. **서브모듈 다섯을 품는다**
  antlr-code-parser · api-gateway

        ↓ release 가 굽는다

robo-architect/desktop/resources/runtime/   설치본에 실릴 것들이 모인다
robo-workspace/_releases/<releaseId>/       설치본 · 매니페스트 · 체크섬
```

## 3-2. 저장소 일곱 + 서브모듈 다섯

`workspace.json` 의 `repositories` 는 일곱인데 **프로필마다 받는 게 다르다.**

| id | 경로 | `architect-electron` 이 받나 |
|---|---|---|
| antlr | `project/antlr-code-parser` | ✔ |
| gateway | `project/api-gateway` | ✔ |
| architect | `project/robo-architect` | ✔ |
| analyzer · catalog · fabric · frontend | `project/robo-data-*` | ✘ (`analyzer` 프로필 전용) |

analyzer 계열은 `robo-architect` 의 **서브모듈**로 온다.

```text
robo-architect/
  open-pencil                        와이어프레임
  robo-analyzer/robo-data-analyzer   분석 엔진
  robo-analyzer/robo-data-catalog    카탈로그
  robo-analyzer/robo-data-fabric     데이터 패브릭
  robo-analyzer/robo-data-frontend   분석기 화면 (MF remote)
```

> **같은 저장소가 두 자리에 나온다.** `analyzer` 프로필은 `project/` 밑의 독립
> 클론을, `architect-*` 프로필은 서브모듈을 쓴다. `robo.ps1` 의 `*-Root()` 들이
> 프로필을 보고 갈라 준다. "클론했는데 왜 안 보이지" 가 여기서 난다.
>
> 서브모듈은 **브랜치가 아니라 커밋을 가리킨다.** `.gitmodules` 의 `branch=main` 은
> `--remote` 갱신용 힌트일 뿐이고, 클론은 부모가 기록한 커밋을 받는다. 그 커밋이
> 원격에 없으면 클론이 실패한다.
>
> ⚠ **2026-10-23 에 실제로 그 직전까지 갔다.** `robo-data-fabric` 의 커밋이
> 부모에는 기록돼 있는데 **원격에는 없었다** — 이 PC 에서는 굽기도 클론도
> 멀쩡했다. 밀어야 할 것을 셀 때 `workspace.json` 의 일곱만 보면 **서브모듈이
> 통째로 빠진다.** 전수로 보는 법:
> `git -C <architect> submodule status --recursive` 로 목록을 얻고,
> 각각에서 `git log @{u}..HEAD` 가 0 인지 본다.

## 3-3. 이미지 열하나 — **저장소와 다른 경로다**

§3-2 는 git 이야기이고, 설치본이 쓰는 것은 도커 이미지다. 둘은 별개다.

```text
소스에서 build (아홉)
  uengine/ontological-db · ontological-bolt        저장소(설계·분석 그래프)
  uengine/robo-authority                           중앙 권한 API + 운영 CLI
  uengine/robo-analyzer · robo-data-catalog
  uengine/robo-data-fabric · robo-antlr-parser
  uengine/robo-api-gateway · open-pencil

레지스트리에서 pull (하나)
  ghcr.io/uengine-oss/process-gpt-bpmn-extractor   GHCR · 태그 고정 · amd64
                                                   ⚠ **우리 소스다** (아래)
```

> ⚠ **"pull 한다" 와 "남의 것이다" 는 다른 말이다** (2026-10-22 정정).
> `process-gpt-bpmn-extractor` 는 **uengine-oss 의 우리 저장소**이고 우리가
> 고쳐 왔다. 다른 점은 소유가 아니라 **포장 방식**이다 — 나머지 아홉은 릴리스
> tar 에 구워 담고, 이 하나만 레지스트리에서 당겨 온다.
> **2026-10-27 부터 남의 제품은 없다.** 마지막 하나였던 `mindsdb` 를 걷어내고,
> 데이터 소스 연합을 `graph-db` 가 직접 한다(PostgreSQL 외부 데이터 래퍼).
> ⚠ 그래서 **사내망에서도 구울 수 있다** — 굽기가 Docker Hub 를 반드시 보던
>   자리가 그 하나였다.

> **`neo4j` 이미지는 없다.** 2026-09-17 에 `graph-db`(Ontological PostgreSQL) +
> `graph-bolt`(Bolt 게이트웨이) 둘로 교체됐다. 코드의 `NEO4J_*` 는 **엔진이 아니라
> 프로토콜의 이름**이다 — 게이트웨이가 Neo4j 프로토콜을 그대로 말하므로 드라이버도
> 변수 이름도 안 바꿨다.

### pdf2bpmn — **우리 소스인데 굽는 길만 다르다**

```text
이미지     태그 고정 (3.35GB · amd64). `robo.ps1` 의 `pdf2bpmn = ghcr.io/…:<커밋>`
우리 코드   robo-architect/desktop/runtime/pdf2bpmn/facade.py  한 파일
          이미지 **밖에** 둔다 → 고쳐도 3GB 를 다시 안 굽는다
          compose 가 그 파일을 마운트하고 entrypoint 를 덮어쓴다
```

**저장소를 고치는 길** (2026-10-22 에 실제로 이렇게 했다):

```text
저장소     github.com/uengine-oss/process-gpt-bpmn-extractor
가지       **enterprise-custom-p** (main 은 안 건드린다)
클론 자리   `project/process-gpt-bpmn-extractor`
          ⚠ `workspace.json` 이 받지 **않는다** — 굽기와 무관하므로 손으로 받는다
이미지로 가는 길
          ① 가지에 커밋을 민다
          ② GitHub Actions 의 **`publish-ghcr` 를 수동 실행**(workflow_dispatch)
             — `on: push` 는 main 에서만 돌므로 가지에서는 수동이 맞다
          ③ 태그는 **커밋 SHA**(`type=sha,format=short,prefix=`)로 붙는다
          ④ `robo.ps1` 과 `runtime-manifest.template.json` 의 핀을 그 SHA 로 바꾼다
          ⑤ **CI 가 지은 이미지를 직접 재서** 확인한다 — 로컬 빌드와 다이제스트가 다르다
```

> ⚠ **이 핀을 안 바꾸면 고친 것이 산출물에 안 닿는다.** 그리고 미루는 동안
> **옛 이미지의 취약점이 늘어난다** — 10-22 에 16 → 37 이 됐다(새 CVE 가 붙어서).

## 3-4. 브랜치가 세 층

```text
1층  workspace 자신         어느 브랜치를 체크아웃했나
2층  workspace.json 의 pin   각 저장소가 **어느 브랜치여야 하는가**
3층  각 저장소의 실제 브랜치   지금 뭘 체크아웃해 뒀나
```

`release` 는 **2층과 3층이 같아야만** 굽는다. pin 은 `workspace.json` 안에 있으므로
고치면 workspace 가 dirty 해지는데 `release` 는 workspace 도 clean 을 요구한다 →
**pin 변경은 커밋돼 있어야 한다.** 그래서 납품용 workspace 브랜치가 따로 있다.

## 3-5. 설정이 사는 곳

```text
robo-workspace/.env              **원본 한 곳**
  ↓ release-environment.json 의 scopes 규칙으로 쪼갠다
runtime/config/analyzer.env · catalog.env · fabric.env
                parser.env · gateway.env · pdf2bpmn.env
runtime/architect/app/.env       백엔드용. **sha256 으로 잠근다**
```

> 스코프에 `prefixes` 를 안 적으면 **그 스코프가 .env 를 통째로 삼킨다.**
> `@($Scope.prefixes)` 가 `$null` 한 개가 되고 `"X".StartsWith("")` 가 참이 된다.
> `"prefixes": []` 를 명시해야 한다. 실제로 걸렸다.

`PDF2BPMN_FACADE_URL` 은 일부러 포장하지 않는다 — 포트가 설치마다 달라서 런처가
실행 시 루프백 주소를 주입한다. `load_dotenv()` 가 `override=False` 라 **주입값이
번들 `.env` 를 이긴다.**

# 4. 자주 헷갈리는 자리

## 4-1. 환경변수가 `.env` 를 이긴다 — **양쪽 모두에서**

```text
앱 쪽       load_dotenv(override=False) → OS 환경변수가 설치본 .env 를 이긴다
            그래서 checksum 에 묶인 .env 를 고칠 필요가 없다
compose 쪽  **셸 환경변수가 .env 파일을 이긴다**
            지난 설치의 ROBO_GRAPH_PASSWORD 가 셸에 남아 있으면 DB 가 그 옛
            비밀번호로 초기화된다. 빈 값으로 남아 있어도 "required variable is
            missing" 으로 기동을 거부한다
```

**2026-10-14 에 둘 다 밟았다.** DB 를 세우기 전에 남은 `ROBO_GRAPH_*` 를 지우고
**창을 새로 열어야** 한다.

## 4-2. 비밀번호는 초기화 때만 쓰인다

볼륨이 이미 있으면 `POSTGRES_PASSWORD` 는 **무시된다.** 설정 파일을 다시 만들어
비밀을 새 난수로 바꾸면 DB 안의 값과 어긋나고, 인증만 실패한다.

```sql
-- 로컬 소켓은 trust 라 옛 값 없이 맞출 수 있다
ALTER ROLE robo PASSWORD '<.env 의 값>';
```

## 4-3. `healthy` 와 `인증이 된다` 는 다른 일

```text
graph-bolt 의 healthcheck   TCP 연결만 본다 → 속이 깨져도 healthy 로 뜬다
graph-db 의 healthcheck     pg_isready **와** og_catalog.graph 표를 같이 본다
                            (pg_isready 만 보면 초기화 거부도 healthy 다 —
                             2026-10-01 에 성공한 줄 알고 넘어갔다)
확인하는 법                  127.0.0.1 로 psql 하면 pg_hba 가 **trust** 라 통과한다.
                            반드시 **TCP 경로**(-h graph-db)로 확인한다
```

## 4-4. 실행 형태가 셋 — 섞으면 계속 헷갈린다

| | 무엇이 뜨나 | Architect API | 도커 스택 | 런처 주입 |
|---|---|---|---|---|
| `./dev.sh` (맥) | 브라우저 | `uv` 로 로컬 | 사람이 따로 | 없음 |
| `robo.cmd up architect-electron` | Electron 창 | `uv` 로 로컬 | 사람이 따로 | **없음** |
| **설치본** | Electron 창 | **번들 Python** | **앱이 띄운다** | **있다** |

가운데가 함정이다. Electron 은 뜨지만 `ROBO_BACKEND_DIR` 이 있어 `usePackagedRuntime()`
이 false → `startDockerStack()` 을 건너뛴다. 그래서 pdf2bpmn 주소를
`robo-architect/.env` 에서 읽는다.

## 4-5. 같은 컴포넌트가 두 곳에 붙는다

`ChatPanel` 은 Design 탭(`CanvasWorkspace`)과 Data 탭(`AggregatePanel`) 양쪽에 있다.
**Inspector 와 오른쪽 자리를 나눠 쓰는 것은 Design 쪽**이고 선점 잠금도 그쪽이다.
검사를 Data 탭에 붙이면 패널이 안 열려 한참 헤맨다.
